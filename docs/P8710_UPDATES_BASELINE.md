## 三、时间语义严格治理（五大时间维度）

严禁使用数据库字段混淆真实软件更新周期，明确以下五种时间语义：

| 时间概念 | 数据库字段/来源 | 业务含义 | 频道展示口径 | 违规禁止项 |
| :--- | :--- | :--- | :--- | :--- |
| **软件首次入库时间** | `Software.createdAt` | 平台首次录入收录该软件的时间 | 仅用于「最新收录 (Newly Added)」专区 | **严禁将入库时间冒充版本更新发布时间** |
| **信息最后编辑时间** | `Software.updatedAt` | 编辑人员修改了软件描述、截图等元数据 | 仅限后台操作审计日志 | **严禁将 updatedAt 冒充软件发布了新版本** |
| **官方版本发布日期** | `SoftwareVersion.releaseDate` | 软件开发商/官方原厂实际发布该版本日期 | 版本时间线、版本详情的核心时间基准 | **若未知必须标注“日期待确认”，严禁自动填充当前时间** |
| **版本更新发现时间** | `VersionCandidate.discoveredAt` | 自动化监测脚本首次探查到版本可能变动的时刻 | 仅供后台审核流参考 | **未核验发现不得直接作为已发布事件展示** |
| **版本核验确认时间** | `VersionCandidate.reviewedAt` | 平台编辑完成版本、来源、安全比对的时刻 | 标识“已核验”或后台审核归档 | **严禁未核验即标记“已通过完整性核验”** |

## 四、当前 `/updates` 页面问题审计

基于代码审查与 Playwright 抓取的基线截图 (`p8710_before_updates_1440.png`, `p8710_before_updates_390.png`)，旧版存在以下严重缺陷：

1. **缺乏 UI 3.0 门户化信息架构**：
   - 仅有两个生硬的 Tab 按钮（`版本更新动态` vs `最新收录入库`），缺少独立的重点更新 Hero、时间范围筛选、类型/分类多维检索、侧边栏数据洞察。
2. **缺乏时间范围与多维筛选**：
   - 仅有一个简单的操作系统过滤按钮（Windows/macOS/Linux），缺少 7天/30天/90天/全部 筛选。
   - 缺少根据 `SOFTWARE` / `TOOL` / `GAME` 资源类型以及业务分类 (系统工具、影音播放、办公等) 的检索能力。
3. **缺少搜索与排序**：
   - 无关键词搜索框，无按照发布时间、核验时间、软件名称排序。
4. **缺少紧凑时间线分组**：
   - 简单的列表平铺，无按日期/周/月的分组标题，阅读体验差。
5. **更新日志展示粗糙**：
   - 直接把 changelog 字符串平铺在卡片内，无折叠/展开机制，长文本占用大量垂直空间；缺少缺失 changelog 时的“官方更新说明暂未收录”兜底友好呈现。
6. **缺少版本历史查询与对比**：
   - 用户无法查看某款软件从旧版到新版的演进历史，无法查看版本差异。
7. **数据孤岛与性能问题**：
   - 前端调用旧 `/api/v1/versions/feed` 接口，该接口缺少时间范围、分类、搜索等服务端分页过滤能力，难以支撑高质量门户体验。
